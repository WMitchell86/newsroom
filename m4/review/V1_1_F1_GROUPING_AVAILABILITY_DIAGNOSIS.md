## 2. Resolution of the F0 count contradiction

**F0's conclusion was under-determined, not wrong — but it was stated with more
confidence than the evidence supported.** The honest position: a Story count
cannot establish a root cause, and F0 used one. F1 replaced it with a partition
comparison.

### Method

A partition is a grouping, not a naming. Story ids are regenerated by any
replay, so ids cannot be compared across partitions. The comparison therefore
uses a **dense cluster index** plus a pairwise co-clustering matrix:

```text
partition      : item_id -> dense cluster index
co-clustering  : {frozenset({a, b}) for every pair a,b in the same cluster}
difference     : symmetric difference of two co-clustering sets
```

This is id-independent and cannot be masked by equal counts.

### Result

| LIVE vs NO_MODEL | value |
| --- | --- |
| stories | 253 vs 263 |
| publications | 300 vs 300 |
| pairs together in both | **47** |
| pairs together only in LIVE | **12** |
| pairs together only in NO_MODEL | **0** |
| affected publications (only-LIVE pairs) | 22 |
| affected clusters (only-LIVE pairs) | 10 |

**LIVE ⊃ NO_MODEL, strictly.** There is no pair that NO_MODEL groups and LIVE
does not. A compensating "live split where no-model merged" would appear as a
non-zero `only_b`. It is **0**.

## 14. Root-cause classification

> ## `B. SEMANTIC_BUDGET_EXHAUSTION`

**Evidence:**

1. 2026-09-25 ledger: 1000 logical calls, 79 ok, **916 skipped**, of which
   **705 `ROLE_HARD_BUDGET`** and 211 `PAID_DISABLED`.
2. Role policy: `hard_calls_day: 100` — a hard ceiling far below the ~1
   consultation per anchored item that grouping 300 items requires.
3. The semantic stage nonetheless completed **9 real merges** that are present
   in LIVE and absent from NO_MODEL (§2) — proving it was reachable and correct
   until the budget ran out.
4. The 5 labelled clusters are **identical** in LIVE and NO_MODEL — those items
   were never classified, consistent with the budget dying partway through the
   corpus.
5. The condition is **live today**: all free routes 429-exhausted until
   2026-09-27T07:00Z, paid routes disabled by policy, preflight returns
   `RoleUnavailable`.

**Not `A. SEMANTIC_PROVIDER_AVAILABILITY`:** routes were reachable (79
successes on the build day). Quota exhaustion contributed but was secondary.

**Not `C. PARSE/REQUEST_FAILURE`:** no parse or schema failures in the ledgers;
5 quota failures only.

**Not `D. CANDIDATE_GENERATION_FAILURE`:** all labelled duplicates reached the
classifier as anchored candidates (§11).

**Not `E. CLASSIFIER_QUALITY`:** the 9 merges it did perform were all correct
(§2), and it was never given budget to attempt the rest.

**`F. MIXED` is a defensible secondary reading** — daily quota (429) and
`PAID_DISABLED` both contribute — but the dominant, actionable cause is the
role budget.

## 15. Is JEV actually needed?

> **Not proven. The evidence points away from it, and the burden of proof is
> not met.**

Against the brief's decision rule:

| Criterion | Status |
| --- | --- |
| 1. Healthy existing classifier recovers essentially the same legitimate false splits? | **UNTESTABLE** — it was starved. Candidates all existed (§11), so the opportunity was there. |
| 2. Precision remains acceptably conservative? | Yes — 12/12 on touched pairs |
| 3. Live fragmentation explicable by a fixable availability/budget condition? | **YES — decisively.** `hard_calls_day: 100` vs a workload needing ~200+ |

**Criterion 3 alone is sufficient to recommend against a JEV dependency.** The
fragmentation is explained by a one-line policy number, and that is a far
cheaper and more reversible fix than a permanent second model in the ingestion
path.

**What JEV does buy today:** it was not starved, so it returned 66/66 correct
merges at 0.8 calls/item. If the semantic budget is *not* raised, JEV would
work as a fallback. But that is a fallback to a misconfiguration, and the
correct fix is to size the budget for the job.

## 16. Operational reliability issue

**There is a real operational defect, and it is about visibility, not policy.**

`on_exhausted: "conservative"` is **correct** and must not change: a false split
is still preferable to a false merge. The problem is that **exhaustion is
invisible at the moment it happens**. The editor sees duplicates days later,
with no signal that grouping was degraded.

Persisted health state exists (`var/model_health.json`), but nothing surfaces
"grouping is currently degraded" to the operator, and no counter records how
many items were grouped while the semantic role was out of budget.

**Designed, not implemented (§17):** a minimal signal —

```text
story semantic classifier: healthy | degraded | unavailable | budget_exhausted
last successful semantic classification: <timestamp>
items grouped while degraded: <count>
```

This would have made the 2026-09-25 exhaustion visible within minutes instead
of being discovered through duplicate Stories in E1. **No monitoring was built
in F1.**
